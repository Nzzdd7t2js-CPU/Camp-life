# 風餐露宿 CAMP LIFE｜營區認領驗證與個資保護規格

版本：草案 v1.0  
狀態：產品設計基準，尚未代表功能已實作或已完成法律審查。

## 1. 目的與基本原則

本平台只核實申請帳號是否有權管理指定營區，不替主管機關認定營區合法性，也不替營主作商業或法律背書。

- 不以「能收取某個 Email」或「控制某個社群帳號」單獨作為經營權證明。
- 優先使用可交叉核對的公開營區資料及營主可控制的官方管道。
- 不預設要求身分證、私人住址、個人手機或完整登記文件。
- 不同營區可採不同驗證方式；無法自動確認時轉人工覆核。
- 同一營區不得因新申請而直接覆蓋既有管理者。
- 未完成驗證及核准前，不授予營區管理權限。
- 任何自動檢查只提供風險提示，不自動作成法律或所有權判斷。

## 2. 認領驗證流程

### 第一步：選定營區與檢查既有狀態
1. 申請人登入後選擇平台既有營區。
2. 系統檢查營區名稱、地址、縣市鄉鎮及資料來源。
3. 檢查是否已有 owner_user_id、待審申請或歷史爭議。
4. 若已有人管理，阻止直接認領，改走管理權移轉／爭議處理。

### 第二步：申請人選擇可行的驗證方式

A. 官方網站控制權：
- 先確認該網站與營區的關聯有可信依據（例如政府公開資料、既有營區官方資料或多個獨立公開來源互相吻合）。
- 再以網站指定頁面放置一次性隨機碼或 DNS TXT 驗證，證明申請人控制該網站。
- 網站控制權只證明控制網站，不單獨證明經營權。

B. 官方社群控制權：
- 先核對該社群帳號是否已由可靠來源連結到該營區。
- 透過官方帳號發布一次性驗證碼或完成平台指定互動。
- 新建立、名稱相似或未有可靠關聯的社群帳號，不可單獨作為核准依據。

C. 公開營區聯絡管道：
- 使用已由可靠來源確認屬於該營區的電話或 Email，進行一次性驗證。
- 只驗證管道控制權；不能單獨證明申請人有管理授權。

D. 現場驗證／人工補充：
- 對沒有網站、社群或可核對聯絡管道的營區，提供現場一次性 QR code／驗證碼流程，或由審核人員安排人工核實。
- 只有在確有必要時才要求補充經營關係證明；允許遮蔽與目的無關的個資。

### 第三步：系統風險檢查
系統只做可客觀自動化的檢查並顯示結果：
- 營區資料與官方／公開來源是否相符。
- 驗證碼是否正確、是否過期或重複使用。
- 是否已有管理者、待審申請或爭議。
- 申請資料是否缺漏或有明顯矛盾。
- 同一帳號短期大量申請、同一營區多帳號申請等風險訊號。

結果分為「資料完整待審」、「需要補件」、「人工核實」、「疑似重複／爭議」。不得只憑演算法分數自動認定經營權。

### 第四步：人工核准
- 初期所有認領均由網站業主最後核准。
- 審核畫面提供營區比對結果、驗證方式、驗證時間、公開來源及風險提示。
- 業主可核准、退回補件或拒絕，必須選擇理由並留下審核紀錄。
- 核准時以資料庫交易／受限 RPC 原子地綁定 campsite.owner_user_id、更新申請狀態及營主角色。
- 若營區已有其他管理者，核准流程必須停止並轉爭議處理；不得直接覆蓋。
- 日後可評估對低風險、強驗證案件簡化流程，但需先經實測與政策審查。

## 3. 個資最小化與資料分級

### 公開資料
營區名稱、公開地址、官方網站／公開社群連結、公開營區聯絡資訊。只顯示已確認可公開的內容。

### 會員基本資料
登入 Email、顯示名稱、角色及會員識別碼。不得提供給其他一般會員任意查閱。

### 認領申請資料
申請帳號、選定營區、申請狀態、驗證方式、聯絡資訊及必要說明。僅申請人與具審核職責的網站管理者可依權限存取。

### 敏感證明資料
預設不收集身分證影本、私人住址或完整證件。若個案確有必要：
- 先說明蒐集目的、必要性、使用範圍、保存期限及當事人權利。
- 允許遮蔽非必要欄位。
- 放在 Supabase 私有 Storage bucket，不可使用公開 URL。
- 以嚴格 RLS／受限後端權限及短效 signed URL 存取。
- 不把證件內容寫進一般文字欄位、日誌、錯誤訊息或公開頁面。
- 設定明確保存期限；審核完成且無爭議後依政策刪除。
- 記錄誰在何時因何目的查看或下載。

## 4. 權限與安全要求

- 啟用 RLS；前端隱藏按鈕不等於安全控制。
- 申請人只能新增及讀取自己的申請；不能自行修改 status、reviewed_by、驗證結果或營主角色。
- 業主審核操作必須由伺服器端受限函式檢查 owner_admin 身分。
- 一般會員不可讀取其他會員 Email、私人聯絡資料或證明文件。
- 營主只能管理 owner_user_id 綁定自己的營區。
- 不得將 Supabase service role key 放在前端。
- 所有角色升級、認領、移轉、拒絕及證明文件存取都應有稽核紀錄。
- 防止重複申請、驗證碼重放、暴力猜測、未授權營區轉移及審核競態。
- 管理員帳號應使用強密碼及可用的多因素驗證；限制管理權限人數。

## 5. 申請告知與法遵工作

正式收集資料前，應由台灣法律專業人士檢視：
- 隱私權政策與個資蒐集告知事項。
- 認領服務條款、授權與爭議處理規則。
- 資料蒐集目的、類別、利用期間、地區、對象及方式。
- 當事人查詢、更正、停止利用及刪除等請求流程。
- 資安事件通報、通知及內部應變流程。
- 平台對營區合法性、營主身分及平台服務範圍的正確說明。

平台不得宣稱「通過認領」等於主管機關認證營區合法，也不得在未查證下公開標示營主身分已獲政府認證。

## 6. 目前程式與資料庫的已知差距

依目前 GitHub main 分支檢視：
- claim_requests 目前以 user_id = auth.uid() 限制申請人新增，申請人與網站業主可讀取自己的／全部申請。
- 目前申請表把聯絡資料及證明說明合併存於 proof_note 一般文字欄位；這不是適合存放證件或敏感附件的設計。
- 業主後台會顯示待審申請的 proof_note。
- 目前 review_campsite_claim RPC 有業主檢查、申請狀態檢查、營區已被其他帳號認領時阻止覆蓋的邏輯。
- 目前尚未建立完整的驗證紀錄、私密證明文件 bucket、短效存取、資料保存期限及審核存取稽核機制。
- 目前後台的會員搜尋與管理功能需要逐項做資料最小化與角色權限測試，不能只依賴前端畫面隱藏。

## 7. 開發順序與驗收條件

1. 盤點實際 Supabase schema、RLS、GRANT、Storage bucket 及 RPC；先備份並確認現況，不執行破壞性 SQL。
2. 修正認領申請欄位與權限：申請人不可自行設定審核欄位或角色。
3. 建立驗證方式及驗證狀態資料模型；驗證碼須隨機、限時、單次使用。
4. 建立私密附件流程（若實際需要），預設不要求證件。
5. 建立業主審核佇列、審核理由、補件及爭議處理。
6. 加入稽核紀錄、保存期限與刪除作業。
7. 以一般會員、營主、網站業主及未登入訪客測試每一項資料存取。
8. 由台灣法律專業人士檢視政策與告知文字後，才開放正式認領。

### 上線前不可妥協的驗收
- 一般會員不能讀取別人的認領申請或證明。
- 申請人不能自行核准、升級營主或變更審核紀錄。
- 任何未驗證或有爭議的申請都不會取得營區管理權。
- 已認領營區不能被另一個帳號直接覆蓋。
- 敏感文件不會產生公開網址。
- 核准、拒絕、查看及刪除等敏感操作可追溯。
- 隱私告知與保存期限已完成法律審閱。
